# Playwright Code Review Checklist (Senior QA)

Этот документ фиксирует обязательные критерии ревью автотестов, чтобы не пропускать критичные антипаттерны и поддерживать стабильность CI.

## Формат вердикта ревью
- **Summary**: краткий итог (готово к merge / нужны правки).
- **Critical Issues**: ошибки, ведущие к flaky/падениям CI.
- **Suggestions for Improvement**: улучшения архитектуры и читаемости.
- **Best Practices**: дополнительные улучшения (API mocking, visual checks и т.д.).

## 1) Локаторы и устойчивость
- Использовать **Web-first locators**:
  - `getByRole`
  - `getByTestId`
  - `getByPlaceholder`
  - `getByLabel`
- Критиковать и избегать:
  - хрупкие XPath;
  - длинные CSS-селекторы, привязанные к DOM-структуре;
  - нестрогие локаторы для одиночных действий.
- Проверять **strictness**: локатор для действия должен однозначно находить один элемент.

## 2) Ожидания и ассерты
- Запрещено: `page.waitForTimeout()` для синхронизации.
- Использовать Web-first assertions:
  - `await expect(locator).toBeVisible()`
  - `await expect(locator).toHaveText(...)`
  - `await expect(page).toHaveURL(...)`
- Проверять, что ассерты подтверждают бизнес-результат, а не только "элемент показался".

## 3) Архитектура и POM
- Локаторы и действия инкапсулировать в Page Object.
- Тесты должны описывать бизнес-сценарий, а не детали UI-реализации.
- Повторяющиеся шаги выносить в:
  - `BasePage` методы;
  - fixtures;
  - helper/utility-слой.

## 4) Изоляция и чистота
- Тесты должны быть независимыми и параллелизуемыми.
- Использовать изоляцию `BrowserContext` по тестам.
- Проверять корректность `beforeEach/afterEach` (или fixtures) для подготовки/очистки.
- Не допускать скрытых зависимостей теста B от результата теста A.

## 5) Диагностика и отчеты
- Проверять наличие/корректность:
  - trace;
  - screenshots (на падениях или по политике проекта);
  - video (по политике проекта);
  - читаемых шагов (`test.step`) при необходимости.

## 6) Антипаттерны (блокирующие)
- Жесткие паузы `waitForTimeout` вместо ожиданий Playwright.
- Дублирование авторизации и тяжелого setup в каждом тесте.
- Выбор сущностей по индексу UI без бизнес-валидации соответствия.
- Локаторы, завязанные только на язык/текст там, где доступен стабильный test id.
- Ассерты только на "видимость модалки" без проверки бизнес-эффекта.

## 7) Минимальный merge gate для E2E
- Нет критичных flaky-рисков в локаторах/ожиданиях.
- Нет жестких пауз.
- Нет архитектурного дублирования ключевых потоков (например login).
- Есть проверка бизнес-результата сценария.
- Доступны артефакты для дебага падений (trace/video/screenshot по конфигу).
